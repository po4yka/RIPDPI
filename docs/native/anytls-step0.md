# AnyTLS Step 0

This note is the pre-implementation review gate for native AnyTLS client support. No Rust or Kotlin implementation should start until this protocol reading, relay-core map, and test plan are reviewed.

- Canonical implementation cross-check: `anytls/anytls-go` `proxy/padding/padding.go`, `proxy/session/frame.go`, and `proxy/session/session.go`, inspected from commit `2012ef89768409f45437f1c06a7af5f6eea402ad`.

`anytls-go` is normative and wins every conflict. `cfal/shoes` is useful for Rust API and task-shaping comparisons only; do not copy code or tests from it.

## Native Scope

`ripdpi-anytls` will be a new Rust lib crate implementing AnyTLS client/outbound behavior only. It must cover TLS 1.3 over BoringSSL, first-packet auth, byte-exact padding scheme handling, session frames, stream multiplexing, UDP-over-TCP, and relay-core integration.

Non-goals to record again in the crate README: AnyTLS server/inbound role, and non-TLS transport substrates. The FAQ explicitly frames TLS as the security layer AnyTLS relies on, and treating other substrates as out of scope keeps RIPDPI aligned with the requested native client path.

## Normative Protocol Facts

- Authentication is sent immediately after TLS handshake as `sha256(password)` plus a big-endian `u16` padding0 length plus padding0 bytes; server-side authentication must fully read padding0 and failed auth may close or fall back to a legitimate L7 application. Source: `protocol.md` "客户端 / 认证" and "服务器 / 认证".
- The session frame header is exactly 7 bytes: `command: u8`, `streamId: u32be`, `data length: u16be`, then data. Source: `protocol.md` "客户端 / 会话".
- Command values are `cmdWaste=0`, `cmdSYN=1`, `cmdPSH=2`, `cmdFIN=3`, `cmdSettings=4`, `cmdAlert=5`, `cmdUpdatePaddingScheme=6`, `cmdSYNACK=7`, `cmdHeartRequest=8`, `cmdHeartResponse=9`, and `cmdServerSettings=10`. Source: `protocol.md` "command".
- `cmdWaste` data must be completely read and silently discarded. Source: `protocol.md` "cmdWaste".
- `cmdSettings` is required at the start of every new session and currently carries UTF-8 `key=value` lines including `v=2`, a real client name/version, and lowercase-hex `padding-md5`. Source: `protocol.md` "cmdSettings".
- A server can reject clients that do not implement `cmdUpdatePaddingScheme` and multiplexing; if it rejects, it sends `cmdAlert` and closes the session. Source: `protocol.md` "服务器 / 会话".
- `cmdUpdatePaddingScheme` is sent when the client's `padding-md5` differs from the server scheme. The client must store the pushed scheme on the client object for that server, and new sessions to that server must use it. Source: `protocol.md` "cmdUpdatePaddingScheme".
- The default padding scheme is the multiline `stop=8` scheme in `protocol.md` "cmdUpdatePaddingScheme". The MD5 is over raw scheme bytes, so goldens must pin exact bytes including line endings chosen by RIPDPI.
- `stop=N` means only packet indexes before `N` are padding-processed; `padding0` is the auth packet and does not support splitting; `padding1+` applies splitting and/or `cmdWaste` padding inside the session layer. Source: `protocol.md` "paddingScheme 具体含义与实现".
- The `c` marker means that if the previous split consumed all user data, the current Write TLS operation returns immediately and does not send later padding chunks. Source: `protocol.md` "paddingScheme 具体含义与实现".
- Packet indexes are counted by Write TLS operations: packet 1 should contain `cmdSettings` plus first-stream `cmdSYN + cmdPSH(target address)`, and packet 2 should be the user's first proxied data packet such as a TLS ClientHello. Source: `protocol.md` "paddingScheme 具体含义与实现".
- If a packet index before `stop` has no rule in the scheme, the packet is sent directly. Source: `protocol.md` "paddingScheme 具体含义与实现".
- Clients must implement session-layer multiplexing. New streams should reuse the newest idle session when available; otherwise create a session whose `Seq` is monotonic within a client. Source: `protocol.md` "复用".
- TCP streams send the target as SOCKS address bytes, then relay bidirectionally. UDP uses sing-box UDP-over-TCP v2 by opening TCP target `sp.v2.udp-over-tcp.arpa`; there is no native UDP substrate. Source: `protocol.md` "代理".
- Protocol v2 adds `cmdSYNACK`, heartbeats, and `cmdServerSettings`; a v2 client assumes v1 behavior until it receives server settings. Source: `protocol.md` "更新记录 / 协议版本 2 - v0.0.8".

## Implementation Cross-Checks

- `anytls-go/proxy/padding/padding.go` parses `stop`, computes lowercase MD5 over raw bytes, stores raw scheme bytes for update frames, treats `c` as `CheckMark=-1`, and emits ranges from the parsed packet-index rule.
- `anytls-go/proxy/session/session.go` sends `cmdSettings` with `padding-md5`, handles `cmdUpdatePaddingScheme` on the client by updating the stored padding factory, sends `cmdServerSettings` for v2 peers, and applies padding in `writeConn()` by packet counter before writing to the TLS stream.
- `anytls-go/proxy/session/session.go` uses `pkt < paddingF.Stop`, so `stop=8` processes packet indexes `0..7`.
- `cfal/shoes/src/anytls/anytls_types.rs` agrees with the 7-byte frame header and command discriminants. Use this only to sanity-check idiomatic Rust boundaries.
- `cfal/shoes/src/anytls/anytls_client_session.rs` cross-checks a useful client shape: auth write, pre-encoded settings buffer, stream IDs, reader/writer tasks, and pending opens. RIPDPI should still design against `ripdpi-relay-mux` and the normative Go behavior, not copy that implementation.

## Relay-Core Touch Points

- New native crate: add `native/rust/crates/ripdpi-anytls` as a workspace lib crate with README non-goals, protocol modules for padding, frames, auth/TLS/session, and tests/goldens.
- TLS transport adapter: extend `native/rust/crates/ripdpi-relay-tls-transports` with `anytls.rs`, exporting `AnyTlsClientConfig`, `AnyTlsSessionFactory`, `AnyTlsSession`, and an AnyTLS UDP-over-TCP datagram adapter. This mirrors Trojan's adapter shape for TLS-backed TCP+UDP and ShadowTLS's factory wiring for nested transport.
- Relay config: add `config/backend/anytls.rs`, include it in `config/backend.rs`, extend `RelayBackendConfig`, `RelayKind`, `config/flat.rs`, and `config/conversions.rs` with AnyTLS fields.
- Relay backend: add `RelayBackend::AnyTls`, update `dispatch_pooled_backend!`, `connect_tcp`, `open_udp_session`, `quic_migration_snapshot`, and `relay_backend_kind_id` tests. AnyTLS should report TCP and UDP support because UDP is exposed through UDP-over-TCP, not native UDP.
- Relay builder and descriptors: add `backend/builder/builders/anytls.rs`, export it from `builders/mod.rs`, register `kind_id = "anytls"` in `transport_descriptor.rs`, and extend `runtime_validation.rs` pools/capabilities. Initial pool policy should be explicit: AnyTLS has protocol-level session multiplexing, but `ripdpi-relay-mux` pooling must not double-multiplex incorrectly; tests should prove the chosen `reusable` value before enabling it.
- Fixture: extend `local-network-fixture` with a minimal offline AnyTLS server sufficient for auth, settings, frame loop, stream echo, UDP-over-TCP v2, multiplexing, and `cmdUpdatePaddingScheme`. The fixture is an oracle, not the production server role.
- Kotlin schema: extend `core/engine-api/src/main/kotlin/com/poyka/ripdpi/core/RelayNativeConfig.kt` and the Rust flat schema together, then bump `RelayNativeConfigSchemaVersion` and Rust `SUPPORTED_NATIVE_CONFIG_SCHEMA_VERSION` in the same slice because the native wire DTO shape changes.
- Kotlin relay selection: add `RelayKindAnyTls`, `AnyTlsRelayKindResolver` or equivalent descriptor-backed resolver, update `RelayKindResolverRegistry`, `RelayKindDescriptor`, validation support, runtime resolver fields, credential persistence, and descriptor drift tests.
- Import wiring: reuse the existing `anytls://`, Clash, and sing-box parser surface rather than reparsing at runtime; the import confirmation path must project AnyTLS profiles into `RelayKind::AnyTls` with server, port, SNI/server name, password, and TLS/certificate fields preserved according to existing profile models.

## Stop Rules

- Do not implement before this Step 0 note is reviewed.
- Every implementation slice starts by adding a failing test and showing the failing `cargo test` or focused Gradle command before source changes.
- Do not skip `cmdUpdatePaddingScheme`, simplify padding, use tautological goldens, use `#[ignore]`, mock the unit under test, delete failing tests, or leave "for now" stubs.
- Do not commit red. Each slice commit must be green for its stated cargo/Gradle scope and must cite the relevant `protocol.md` sections in the commit body.
