# Rust WebTunnel Step 0

This note is the review gate for replacing the Go `ripdpi-webtunnel` pluggable transport binary with an in-repository Rust crate. No implementation should start until the fingerprint approach and test plan below are accepted.

## Canonical Inputs

- Standalone WebTunnel source: `gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/webtunnel`, read from a fresh clone at `/tmp/ripdpi-step0-webtunnel`.
- Current RIPDPI upstream binary source: `gitlab.torproject.org/tpo/anti-censorship/pluggable-transports/lyrebird`, read from a fresh clone at `/tmp/ripdpi-step0-lyrebird`; this is the source currently pinned by `native/pluggable-transports/sources.json`.
- Tor PT spec: `tpo/core/torspec`, `attic/text_formats/pt-spec.txt`, read from `/tmp/ripdpi-step0-torspec`.
- RIPDPI integration points: `core/service/src/main/kotlin/com/poyka/ripdpi/services/PluggableTransportManager.kt`, `core/service/src/main/kotlin/com/poyka/ripdpi/services/PluggableTransportSocksBridge.kt`, `build-logic/convention/src/main/kotlin/ripdpi.android.rust-native.gradle.kts`, and `native/pluggable-transports/sources.json`.

## Scope

The Rust crate will implement WebTunnel client mode only. It will parse WebTunnel bridge arguments, establish a browser-mimicking TLS connection, issue the HTTP/1.1 Upgrade request to the secret URL path, expose a local SOCKS5 listener through the Tor PT managed-client protocol, and carry raw bytes after a successful `101 Switching Protocols` response.

Non-goals: WebTunnel server/bridge mode, and byte-perfect browser/uTLS parity. The target is best-effort browser camouflage through BoringSSL with packet-level golden tests against an explicit uTLS profile; the README for the new crate must say this plainly.

## Protocol Constants From Go

- `url` is the primary client argument. Lyrebird parses it as `http` or `https`, sets TLS on for `https`, derives the secret path from the escaped URL path without the leading slash, sets HTTP `Host` to `url.Hostname()`, defaults SNI to `url.Hostname()`, and defaults the TCP endpoint to `url.Hostname():443` for HTTPS or `url.Hostname():80` for HTTP. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:53-83`.
- `addr` overrides the derived TCP endpoint after `url` parsing. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:76-80`.
- `servername` overrides the SNI value. Lyrebird also supports `sni-imitation` and multiple comma-separated server-name candidates through its generator, but RIPDPI currently passes only `url` and `utls`. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:85-92` and `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/servername_generator.go`.
- `utls` selects the uTLS ClientHello. Lyrebird maps `none` to regular Go TLS, maps an empty supplied value to `hellorandomizednoalpn`, and defaults a missing value to `hellorandomizednoalpn`; `utlsutil` maps `hellochrome_auto` to `utls.HelloChrome_Auto` and its empty parser default to `HelloChrome_Auto`. RIPDPI currently supplies `utls=hellochrome_auto`, so the Rust drop-in should honor that input and target Chrome unless this Step 0 review changes the target. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:94-105` and `/tmp/ripdpi-step0-lyrebird/common/utlsutil/clienthelloID.go:9-67`.
- `cert` and `cert-domain` exist in current lyrebird for certificate-chain pinning and verification-domain override. They are not named in the requested normative constants, but tests should include parser preservation/rejection decisions so this is not silently lost. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:107-112` and `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/utls.go:58-80`.
- The client dials TCP, then TLS if enabled, then HTTP Upgrade. The HTTP request is `GET /{path} HTTP/1.1` with `Connection: upgrade`, `Upgrade: websocket`, and `Host` equal to the URL hostname; success requires status text `101 Switching Protocols` plus `Upgrade: websocket` and `Connection: upgrade`, then the connection becomes a raw tunnel. Reference: `/tmp/ripdpi-step0-lyrebird/transports/webtunnel/client.go:127-201` and `/tmp/ripdpi-step0-webtunnel/transport/httpupgrade/httpupgrade.go:32-58`.

## TLS Fingerprint Plan

Use `boring` and the existing `ripdpi-tls-profiles` crate, not `rustls` or `native-tls`, for the bridge connection. The initial target profile should be `chrome_stable` because RIPDPI currently passes `utls=hellochrome_auto` for WebTunnel and `ripdpi-tls-profiles` already exposes a BoringSSL Chrome profile with GREASE enabled, extension permutation enabled, TLS 1.2 through TLS 1.3, Chrome-like cipher/group/signature configuration, and packet golden coverage.

Parity expectation versus uTLS is not byte-perfect. BoringSSL can approximate Chrome with cipher list, supported groups, signature algorithms, ALPN, GREASE, and extension permutation, but it does not expose all uTLS-level knobs for exact extension byte layout and future Chrome drift. The acceptance target should therefore be structural parity, not identity: same intended browser family, SNI present and equal to the resolved server name, TLS 1.3 offered, GREASE present when the Chrome profile says so, supported groups include the Chrome profile set, ALPN policy explicitly decided, JA3/JA4 fixture fields stable, and no accidental fallback to regular Rust TLS.

Open review question: WebTunnel is an HTTP/1.1 Upgrade protocol. `hellochrome_auto` may advertise browser ALPN, while lyrebird’s own missing-`utls` default is `hellorandomizednoalpn`. Keeping RIPDPI drop-in behavior points to Chrome, but the implementation must test that the local fixture either selects no ALPN or `http/1.1`; if a server selects `h2`, the client must fail before writing an HTTP/1.1 Upgrade over an HTTP/2-negotiated TLS channel.

## RIPDPI PT IPC Contract

`PluggableTransportManager` starts `ripdpi-webtunnel` with no command-line arguments and these environment variables: `TOR_PT_MANAGED_TRANSPORT_VER=1`, `TOR_PT_STATE_LOCATION=<app files>/pluggable-transports/<profile>-webtunnel`, `TOR_PT_CLIENT_TRANSPORTS=webtunnel`, and `TOR_PT_EXIT_ON_STDIN_CLOSE=1`. Reference: `core/service/src/main/kotlin/com/poyka/ripdpi/services/PluggableTransportManager.kt:148-168` and `core/service/src/main/kotlin/com/poyka/ripdpi/services/PluggableTransportManager.kt:197-209`.

The subprocess must write PT messages to stdout. The app accepts readiness from `CMETHOD webtunnel socks5 <host>:<port>` and then bridges its own local SOCKS side to that listener with SOCKS5 username/password carrying escaped PT args. Reference: `core/service/src/main/kotlin/com/poyka/ripdpi/services/PluggableTransportSocksBridge.kt:31-58`.

The Tor PT spec requires version negotiation with `VERSION 1` or `VERSION-ERROR`, client listener reporting through `CMETHOD <transport> <socks4|socks5> <address:port>`, a final `CMETHODS DONE`, and graceful shutdown on stdin close when `TOR_PT_EXIT_ON_STDIN_CLOSE=1`. Reference: `/tmp/ripdpi-step0-torspec/attic/text_formats/pt-spec.txt:171-217`, `/tmp/ripdpi-step0-torspec/attic/text_formats/pt-spec.txt:493-558`, and `/tmp/ripdpi-step0-torspec/attic/text_formats/pt-spec.txt:711-734`.

Gradle currently builds one Go lyrebird binary from `native/pluggable-transports/sources.json` and emits three launchers, including `ripdpi-webtunnel`. The only requested integration change is to point this PT source manifest at the in-repo crate rather than the Go repo, which likely requires extending the manifest/build task schema to support a Rust package artifact while keeping `PluggableTransportManager` untouched. Reference: `native/pluggable-transports/sources.json:5-17` and `build-logic/convention/src/main/kotlin/ripdpi.android.rust-native.gradle.kts:548-760`.
