# Relay Chain STEP 0 Audit And UX Plan

## Findings

- Chain configuration is fixed two-hop today. `ChainRelayConfig` has entry and exit scalar fields plus `entry_profile_id` / `exit_profile_id`; there is no list-like hop model in Rust or Kotlin wire DTOs.
- Chain profile references already exist in Kotlin UX/storage, but they are not heterogeneous. `resolveChainRelayHopSupport()` loads entry/exit profile IDs, rejects self-reference, then rejects every kind except `RelayKindVlessReality` and rejects VLESS xHTTP, so current profile references are UX/storage sugar over direct VLESS Reality TCP hops only.
- The native relay wire contract is still inline VLESS-shaped. `ResolvedRipDpiRelayConfig` and `FlatResolvedRelayRuntimeConfig` carry `chainEntryServer`, `chainEntryPublicKey`, `chainEntryUuid`, and matching exit fields; they do not carry each hop's `kind` or backend-specific sections.
- The Rust runtime is VLESS-specific inside `ChainRelaySessionFactory`. The chain builder converts both hops with `vless_reality_config()`, and `open_stream()` dials the exit through `VlessRealityClient::connect()` / `connect_with_bind()` for the entry and `VlessRealityClient::connect_over()` for the exit. The existing nested transport behavior must be preserved, but heterogeneous hops require moving the chain hop representation onto the existing relay backend/session abstractions instead of adding a separate transport path.
- Chain UDP is correctly non-goal for this feature. `ChainRelaySessionFactory::capabilities()` advertises `udp=false`, and `open_datagram()` returns `Unsupported`.
- Current fail-closed behavior exists at the SOCKS request boundary but is under-tested for chain-specific dead-hop cases. `handle_connect()` calls `backend.connect_tcp()`, emits a failure observation on any error, records `lastHandshakeError`, writes a SOCKS failure reply, and returns the error; there is no direct bypass path in that function.
- Current chain telemetry is coarse. `RelayTelemetry` exposes only `chain_entry_state` and `chain_exit_state`, and `chain_state()` maps both to `connected` whenever the runtime is running. It does not distinguish entry failure from exit failure and has no per-hop latency fields.
- Per-hop DNS bootstrap is not modeled for chain hops yet. Existing relay endpoint bootstrap resolves active chain entry and exit hostnames directly before runtime start; DNS-over-relay exists in the tunnel path, so chain implementation needs to compose with that policy for hop bootstrap without allowing post-bootstrap direct DNS leaks.
- Trust-domain metadata does not exist on relay profiles. `RelayProfileRecord` has no jurisdiction or operator fields, so same-domain detection cannot be implemented without extending the profile model and UI state.
- Chains longer than two hops are not cheap in the current contract. The storage, native DTO, Rust config, telemetry, and UI are all entry/exit-shaped, so N-hop support should stay a follow-up unless a separate schema/list migration is explicitly accepted.

## Model Direction

- Keep the public feature fixed at two hops for this slice set: entry and exit.
- Add a heterogeneous hop model to the native relay wire contract: each chain hop needs at least `profileId`, `kind`, common endpoint fields, credentials references/values already allowed for that backend family, and backend-specific sections needed by supported in-process kinds.
- Reuse existing backend builders and `RelayBackend::connect_tcp()` semantics for hop execution. The implementation should generalize chain composition through the current relay backend/session layer and must not duplicate VLESS, MASQUE, Trojan, AnyTLS, Shadowsocks, or TUIC connection logic.
- Keep `udpCapable=false` for chain relay and reject UDP enablement when the selected relay kind is `chain_relay`.
- Add `operator` and `jurisdiction` metadata to relay profiles, then derive same-domain warnings from normalized `(operator, jurisdiction)` pairs. Missing metadata should not silently imply safety; it should produce an incomplete-domain warning distinct from same-domain correlation risk.
- Surface warning, not hard-block, for same trust domain unless validation discovers the chain is otherwise incomplete. The security property is user-visible informed consent, not preventing every possible weak chain.

## TDD Plan

- Slice 1, heterogeneous hop config: first add failing Kotlin tests in `UpstreamRelayRuntimeConfigResolverTest` proving a chain can reference `entry=vless_reality` and `exit=masque` and that unsupported recursive/self-referential chains are rejected; add failing `RelayNativeConfigTest` / `NativeConfigSchemaVersionTest` expectations for new per-hop wire fields and schema version; add failing Rust serde/round-trip tests in `ripdpi-relay-core` proving both hop kinds survive JSON decode/encode. Minimal implementation: extend profile resolution into a typed two-hop native model, bump `RelayNativeConfigSchemaVersion` and Rust `SUPPORTED_NATIVE_CONFIG_SCHEMA_VERSION`, update generated/golden fixtures with `RIPDPI_BLESS_GOLDENS` only after non-tautological assertions fail. Protected property: entry and exit accept different backend families without falling back to VLESS-only inline fields.
- Slice 2, fail-closed dead hop: first add a failing relay-core/runtime test using local-network-fixture where the entry backend is reachable and the exit backend is unavailable, then assert the SOCKS CONNECT fails, `lastHandshakeError` records the failing hop, and no direct target connection is observed. Minimal implementation: preserve error propagation through chain `connect_tcp()` and add explicit hop labels in errors if needed. Protected property: a dead hop fails the whole chain and never silently routes around the chain.
- Slice 3, trust-domain model: first add failing data/model tests for `RelayProfileRecord` jurisdiction/operator persistence and normalization plus same-domain detection cases: same operator, same jurisdiction, missing metadata, and genuinely distinct domains. Minimal implementation: add profile metadata fields, a pure trust-domain evaluator, and validation/warning UI state. Protected property: users cannot mistake two same-domain hops for anti-correlation.
- Slice 4, chain editor UI: first add failing ViewModel tests for add/select/reorder/validate fixed two-hop chain references and failing Compose tests for the editor showing hop cards, backend labels, jurisdiction/operator labels, same-domain warning, missing-metadata warning, and validation errors. Minimal implementation: replace the two raw profile ID text fields with an editor backed by saved relay profiles, fixed entry/exit positions, and reorder controls that swap entry and exit. Protected property: chain setup is first-class UX and cannot hide trust-domain risk.
- Slice 5, per-hop status, latency, and DNS bootstrap: first add failing Rust telemetry tests for per-hop state and latency, failing Kotlin snapshot decode/golden tests for the new fields, and failing DNS-over-relay tests proving chain bootstrap composes with the existing relay DNS fail-closed policy after the allowed initial endpoint bootstrap. Minimal implementation: add per-hop telemetry fields, plumb native snapshot decode/UI display, and reuse the existing DNS-over-relay route/fail-closed machinery for chain hop resolution after bootstrap. Protected property: users can see which hop is degraded and chain DNS does not create a direct leak.

## Verification Gates Per Green Slice

- Rust: `cargo fmt --all --manifest-path native/rust/Cargo.toml`, targeted `cargo test -p ripdpi-relay-core ...`, relevant fixture/E2E tests, `cargo clippy --workspace --all-targets --manifest-path native/rust/Cargo.toml -- -D warnings`, and existing `cargo deny` gate before final DONE.
- Kotlin/Android: targeted Gradle unit tests for modified modules first, then `./gradlew :core:engine:testDebugUnitTest :core:service:testDebugUnitTest :app:testDebugUnitTest`, relevant Compose UI tests, `./gradlew staticAnalysis`, and schema/golden tests with blessings only after a failing test proves the expected delta.
- Runtime oracle: local-network-fixture E2E with two fixture backends, including `Reality -> MASQUE -> exit` and dead-exit fail-closed cases.
- Commit rule: one Conventional Commit per green slice, scoped `chain`, with the body citing the primary files changed and the test commands run. No implementation commit may be made while any targeted slice gate is red.

## Review Questions

- Should same jurisdiction but different operator warn with the same severity as same operator, or should the UI distinguish "same jurisdiction" from "same operator" while treating both as anti-correlation risk?
- Should missing jurisdiction/operator block saving, or warn and allow saving? The plan above warns and allows saving to avoid making metadata entry a hard prerequisite for imported profiles.
- Should Slice 1 support all in-process TCP backends immediately, or only the minimum heterogeneous path needed for `Reality -> MASQUE -> exit` plus explicit unsupported errors for the rest?
